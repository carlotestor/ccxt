This block already knows *which* risk order it is, but throws that away by routing both branches into the generic `triggerPrice`. The unified order structure has dedicated fields, and `safeOrder` passes `stopLossPrice` / `takeProfitPrice` straight through (`ts/src/base/Exchange.ts:5031-5032`) — so both come back `null` on these rows today.

Since `createOrder` accepts `params.stopLossPrice` / `params.takeProfitPrice` to place them, the round trip is asymmetric. Splitting the branch keeps the cost at two lines:

```ts
let stopLossPrice: Str = undefined;
let takeProfitPrice: Str = undefined;
if (rawSide === 'STOPLOSS') {
    stopLossPrice = priceString;
} else if (rawSide === 'TAKEPROFIT') {
    takeProfitPrice = priceString;
}
```

then pass them in alongside `triggerPrice`. Note `isTriggerOrSLTpOrder` (line 4788) already keys off all three, so the `IOC` suppression you get today is preserved either way.

===== ts/src/mudrex.ts:769-772 len=903 =====
Keeping the raw payload out of `info` is a genuine improvement, but assigning `type`/`side` *after* `parseOrder` means `safeOrder` never sees them. The create response omits `trigger_type`, so `typ` is now `undefined` at `safeOrder` time and the `timeInForce` branch at `ts/src/base/Exchange.ts:4989` (`type === 'market'` → `'IOC'`) no longer fires — a market `createOrder` that used to return `timeInForce: 'IOC'` now returns `undefined`.

Passing a copy into the parser instead keeps the base derivation intact without touching `data`:

```ts
const parsed = this.extend (data, {
    'order_type': request['order_type'],
    'trigger_type': request['trigger_type'],
});
return this.parseOrder (parsed, market);
```

(trade-off: `info` carries the two restored keys again). Either way the new `fetchOrder` fixture only covers a limit order — a market-order case would pin whichever behaviour you intend.
